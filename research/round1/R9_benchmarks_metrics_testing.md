## Part A — Document-conversion benchmarks & metrics in use (2024–2026)

### A.1 OmniDocBench (OpenDataLab / CVPR 2025)

**Sources:** [github.com/opendatalab/OmniDocBench](https://github.com/opendatalab/OmniDocBench), [arxiv.org/abs/2412.07626](https://arxiv.org/abs/2412.07626)

OmniDocBench is the closest thing the field has to a standard, multi-tool leaderboard for PDF→structured-output quality as of 2026. Key facts confirmed from the repo/paper:

- **Dataset:** 1,651 PDF pages (v1.x baseline) spanning **10 document types** (academic papers, textbooks, financial reports, newspapers, handwritten notes, etc.), **5 layout types**, **5 languages**, with **19 layout categories** and **15 attribute labels** for fine-grained slicing. v1.6 added 296 new pages targeting harder scenarios (dense tables, rotated pages, low-quality scans). Accepted at **CVPR 2025**.
- **License:** Apache-2.0 — permissive, safe for OpenConvert to vendor a subset as a fixture/oracle corpus.
- **Metrics (per task):**
  - **Text:** *Normalized Edit Distance* (character-level Levenshtein distance normalized by max(len(pred), len(gt))), also reporting BLEU/METEOR as secondary signals.
  - **Text normalization / segmentation for fairness:** paragraphs are segmented on double line breaks, then an **"Adjacency Search Match"** procedure aligns predicted vs. ground-truth blocks to absorb differences in how tools merge/split/truncate paragraphs before edit distance is computed — i.e., the benchmark explicitly tries not to penalize a tool for reflowing text differently than the reference, only for actually losing/garbling content.
  - **Tables:** **TEDS** (Tree-Edit-Distance-based Similarity, see A.14) plus a raw table Edit Distance.
  - **Formulas:** **CDM** (Character Detection Matching — a formula-recognition-specific edit-distance/matching metric) plus formula Edit Distance.
  - **Reading order:** Edit Distance over the predicted block sequence vs. ground-truth order.
  - **Composite "Overall" score:** `((1 − text_edit_distance) × 100 + table_TEDS + formula_CDM) / 3` — a simple unweighted average of the three headline sub-scores, expressed on a 0–100 scale.
  - Results are broken down **per page-type/attribute** (e.g., dense text, multi-column, rotated, watermarked, table-heavy) rather than only as one aggregate — this per-slice breakdown is the part most directly reusable for OpenConvert's own regression dashboard.
- **Published baselines (OmniDocBench v1.6 leaderboard, as fetched):**
  | Tool | Overall score |
  |---|---|
  | PaddleOCR-VL-1.6 (VLM-based) | 96.34 |
  | MinerU2.5-Pro | 95.75 |
  | GLM-OCR | 95.22 |
  | Marker (pipeline) | 78.44 |
  | Docling | reported, exact score not captured in fetch — see A.2 |

  These numbers show the current (2026) state of the art clusters **95–96** for the best VLM/hybrid pipelines, while classical "deterministic pipeline" tools (Marker's non-LLM heuristic mode, Docling) trail meaningfully (high-70s to low-80s on this particular leaderboard cut). This is a directly useful anchor for OpenConvert's own thresholds (§A.16).

### A.2 Docling / docling-eval (IBM / DS4SD, now Linux Foundation "docling-project")

**Sources:** [github.com/docling-project/docling-eval](https://github.com/docling-project/docling-eval), [arxiv.org/abs/2408.09869](https://arxiv.org/abs/2408.09869) (Docling technical report)

- docling-eval is a **standalone evaluation harness**, not a single fixed benchmark — it wraps multiple external benchmark datasets under one CLI/metric pipeline:
  - **DP-Bench:** text, layout, reading order, table structure.
  - **OmniDocBench:** text, layout, reading order, table structure (i.e., docling-eval re-implements/consumes the OmniDocBench protocol rather than inventing a competing one).
  - **DocLayNet v1.2:** text + layout only.
  - **FinTabNet, PubTabNet, Pub1M:** table-structure-specific evaluation.
- **Workflow shape:** a two-step CLI — (1) *create* ground-truth + prediction datasets in a unified internal format, (2) *evaluate* predictions against ground truth per metric family. This "materialize predictions once, evaluate many metrics against a canonical IR" pattern is directly relevant to OpenConvert's own harness design (§D.5) — Docling's own approach validates building a canonical intermediate JSON representation as the evaluation substrate rather than scoring straight off raw output formats.
- **License / positioning:** Docling itself is **MIT-licensed** (per the technical report fetch), self-contained, uses DocLayNet-trained layout model + TableFormer for tables — i.e., a deterministic, non-LLM pipeline by default, architecturally close to what OpenConvert is building. Its Marker/OmniDocBench-leaderboard scores (mid-to-high 70s to 80s depending on version/leaderboard) represent a realistic **non-LLM deterministic-pipeline ceiling** to benchmark OpenConvert against, rather than comparing OpenConvert only to VLM-based tools that need GPUs.

### A.3 Marker — heuristic score vs. LLM-graded score

**Source:** [github.com/datalab-to/marker](https://github.com/datalab-to/marker)

This is the single most directly relevant precedent for R9 because Marker's README explicitly documents *adopting olmOCR-bench* (see A.5) as its scoring harness rather than inventing its own metric — strong evidence that a **unit-test-style pass/fail suite** is becoming the de facto standard for this space, not just an academic curiosity.

- Marker reports **quality scores 0–100** across the same 8 olmOCR-bench categories (math, tables, reading order, headers/footers, old scans, etc.), computed via **olmOCR-bench's own official checker tool** — i.e., Marker did not build a custom scorer; it consumes an external, independently-maintained pass/fail harness. This is a template OpenConvert should copy: adopt (not reinvent) an external assertion-based benchmark as one CI gate.
- **Two scoring modes exist in the ecosystem**: a cheap **heuristic** score (rule-based / string-assertion checks, what olmOCR-bench itself is) vs. an **LLM-judge** score (e.g., using Gemini as a grader) — Marker's README frames its own comparisons primarily around the heuristic olmOCR-bench numbers, using LLM-graded numbers (e.g., "Gemini Flash 3.5 (API): 76.4% overall") only as one more point of comparison, not as the primary oracle. **Implication for OpenConvert:** prefer heuristic/assertion-based scoring as the *primary*, cheap, deterministic CI signal; treat LLM-as-judge scoring as a secondary, higher-variance, opt-in signal (nightly only), consistent with Part C's guidance on not trusting non-deterministic graders in fast CI.
- **Published comparative numbers (fetched):**
  | Tool / mode | olmOCR-bench overall | Throughput |
  |---|---|---|
  | Marker balanced (GPU) | 76.0% | 2.9 pages/sec |
  | Marker fast (GPU) | 66.6% | 7.4 pages/sec |
  | Marker fast, no OCR (CPU) | 43.6% | 23.7 pages/sec |
  | MinerU (pipeline backend) | 72.7% | — |
  | Docling | 50.3% | — |
  | Gemini Flash 3.5 (API, LLM) | 76.4% | — |

  This table is extremely useful for OpenConvert's own threshold-setting: it shows a **CPU-only, no-OCR deterministic mode lands around 43–50%** on a hard unit-test suite, while adding OCR/heavier processing buys roughly +25–30 points, and LLM-judge/VLM approaches only add a further few points over a good heuristic pipeline (76.0 → 76.4) — i.e., **diminishing returns from LLM involvement once a solid deterministic pipeline exists**, which validates OpenConvert's "deterministic-first, small-LLM-repair-as-a-narrow-patch" architecture rather than an LLM-centric one.

### A.4 MinerU evaluation

**Source:** [github.com/opendatalab/MinerU](https://github.com/opendatalab/MinerU)

- MinerU evaluates on **OmniDocBench** (v1.5 and v1.6 cited in its own changelog) rather than a bespoke benchmark, reinforcing OmniDocBench's role as the shared leaderboard.
- Reported **End-to-End Overall** scores (OmniDocBench v1.6): pipeline backend 86.47; hybrid backend high-effort 95.39; hybrid medium-effort 95.26; VLM engine 95.30. MinerU's own release notes note an OCR-model upgrade improved OmniDocBench accuracy by **~11%**, and that dropping from "high" to "medium" effort in the hybrid backend costs only **0.13 points** while buying **35–220% speed**. This is good evidence for OpenConvert's own "quality vs. speed budget" tier design (§B.9, §D.5) — small quality losses can buy large latency wins, and that tradeoff is worth exposing as a config knob with measured, not guessed, deltas.

### A.5 olmOCR-bench (AllenAI) — the TDD-relevant benchmark

**Source:** [github.com/allenai/olmocr](https://github.com/allenai/olmocr)

This is the **most directly relevant precedent for OpenConvert's own test philosophy**, because it is explicitly structured like a unit-test suite rather than a similarity-score benchmark:

- **~7,000+ test cases across ~1,400 documents** (Marker's README cites "1,403 PDFs with ~8,400 pass/fail unit tests" for its evaluated snapshot — the exact case count varies slightly by benchmark version, both figures fetched from primary sources).
- **8 test categories**: ArXiv (academic content), Old scans math, Tables, Old scans (general historical), Headers & footers, Multi-column, Long tiny text, Base.
- **Scoring:** each test case is a **pass/fail assertion about a specific, verifiable document fact** (e.g., "this exact string must appear before that one in reading order," "this table cell value must be present," "this header text must NOT appear in the body") — not a fuzzy similarity score. The overall score is a **percentage of assertions passed**, reported per category with **explicit margin-of-error** (e.g., "82.4 ± 1.1"), which signals the benchmark authors treat statistical uncertainty as first-class, not an afterthought.
- **Baseline (fetched):** olmOCR v0.4.0 scores **82.4 ± 1.1** overall, ranking near the top among ~11 compared tools (including Marker, Mistral OCR API, DeepSeek-OCR).
- **Why this matters for OpenConvert specifically:** olmOCR-bench's design — *hand/programmatically authored assertions about specific document facts, run per-file, aggregated as a pass rate with confidence intervals* — is structurally identical to what a TDD-built pipeline should be doing internally as its own regression suite, just generalized across a public corpus instead of a private one. **Recommendation: OpenConvert should build its internal fixture corpus using the same pattern (small hand-made PDFs + explicit fact assertions, not just snapshot diffs) and, where license permits, directly incorporate a subset of olmOCR-bench documents/assertions as an external validation set** distinct from its own dogfooded fixtures (avoids overfitting to self-authored tests).

### A.7 READoc — PDF→Markdown end-to-end benchmark

**Source:** [arxiv.org/abs/2409.05137](https://arxiv.org/abs/2409.05137) (confirmed as the READoc paper on fetch)

- **Goal:** evaluates "Document Structured Extraction" (DSE) — converting raw PDFs directly into semantically-rich **Markdown**, end-to-end, rather than scoring intermediate layout/OCR artifacts in isolation. This is the closest published academic framing to OpenConvert's own PDF→EPUB(→effectively structured HTML/XHTML) task shape.
- **Dataset:** **3,576** diverse real-world documents sourced from **arXiv, GitHub, and Zenodo** (i.e., includes non-academic, non-paper documents — READMEs, preprints, reports — which is a broader source mix than most OCR benchmarks).
- **Evaluation architecture — "DSE Evaluation Suite"** with three explicit stages: **Standardization** (normalize both prediction and reference into a common representation), **Segmentation** (break the standardized doc into comparable structural units), **Scoring** (compute similarity per unit and aggregate). This three-stage Standardize→Segment→Score pattern is a strong template for OpenConvert's own PDF→EPUB scorer (canonicalize both the produced EPUB's extracted text/structure and a reference into the same IR before diffing — directly consistent with the "canonical JSON IR" snapshot-testing guidance in Part B).
- **Finding:** evaluating pipeline tools, specialized vision models, and general VLMs together, the authors report a **substantial gap** between current tool performance and their realistic, unified DSE objective — i.e., even in 2024–2025, no tool was close to "solved" on genuinely end-to-end, realistic PDF→Markdown conversion. This is a useful expectation-setting data point: OpenConvert should not target "near-100%" on a genuinely end-to-end metric; per-stage metrics (layout, table, reading order individually) are where "good" scores in the 90s are realistic (per OmniDocBench numbers in A.1), but end-to-end composite scores on hard/diverse corpora should be expected to be meaningfully lower.

### A.8 Grobid — header/structure F1

**Source:** [github.com/kermitt2/grobid](https://github.com/kermitt2/grobid)

Grobid is the standard tool/benchmark reference for **bibliographic/header field extraction** rather than full-document layout, but its evaluation methodology is a useful precedent for *field-level F1 evaluation* of structured extraction (directly analogous to evaluating whether OpenConvert correctly extracts title/author/heading-level metadata into EPUB nav/metadata):

- **Reference extraction F1 ≈ 0.87** on an independent PubMed Central set (1,943 PDFs, 90,125 references), **≈0.90** on a comparable bioRxiv set.
- **Reference parsing in isolation:** **>0.90 F1 at instance-level**, **0.95 F1 at field-level** — i.e., once you've correctly segmented "this is a reference," field-level accuracy (author, title, year, etc.) is much higher than end-to-end instance accuracy. This instance-vs-field split is a useful pattern for OpenConvert to adopt for heading/TOC extraction: separately measure "did we correctly detect that this line is a heading" (instance-level) vs. "did we assign it the correct level/text" (field-level), since these have different failure modes and different appropriate remediation (deterministic rule vs. LLM repair).
- **Citation-context resolution:** 0.76–0.91 F1 depending on collection — showing meaningful **variance by corpus type**, another argument for OpenConvert's per-page-type/per-corpus-slice reporting rather than one aggregate number.

### A.10 Nougat — exact metrics (Meta AI)

**Sources:** [arxiv.org/abs/2308.13418](https://arxiv.org/abs/2308.13418), [github.com/facebookresearch/nougat](https://github.com/facebookresearch/nougat) — and the actual `nougat/metrics.py` source, fetched directly:

This is the one benchmark in this report where the **exact metric implementation** (not just a paper description) was retrieved, which is valuable because it shows precisely how "edit distance / BLEU / METEOR / precision / recall / F1" are computed in a real, widely-cited tool:

- **Edit distance:** `edit_distance(pred, gt) / max(len(pred), len(gt))` — i.e., raw Levenshtein distance normalized by the longer sequence's length (character-level, not word-level, based on the code's use pattern). Same normalization family as OmniDocBench's text metric (A.1).
- **BLEU:** `nltk.translate.bleu([reference], hypothesis)` on **word-tokenized** text.
- **METEOR:** `nltk.translate.meteor([reference], hypothesis)` on word-tokenized text; the code explicitly catches lookup errors and returns NaN rather than crashing — a small but relevant robustness pattern (metric functions should degrade to "undefined/skip," not fail the whole run, on edge-case inputs).
- **Precision / Recall / F-measure:** computed via `nltk.scores.{precision,recall,f_measure}` on **sets of word tokens** (bag-of-words, not sequence-aware) — i.e., Nougat's precision/recall are a coarse "did the right words appear" check, not a structural/positional metric.
- **Normalization applied:** a **minimum length threshold (4 characters)** — predictions/references shorter than this are excluded from scoring (avoids degenerate high/low scores on trivially short snippets). Notably, the fetched code does **not** show explicit lowercasing, punctuation stripping, Unicode normalization, or ligature/hyphenation handling in the metrics function itself — **[UNVERIFIED]** whether such normalization happens upstream in Nougat's dataset-loading code (not fetched); this is a gap OpenConvert should be more careful about (see A.16/C recommendation on Unicode NFC normalization and hyphenation-aware diffing, which Nougat's metrics.py apparently does *not* handle at the metric-computation layer).

### A.11 Reading-order metrics: ARD, Kendall tau, BLEU-on-blocks

**Source:** [arxiv.org/abs/2108.11591](https://arxiv.org/abs/2108.11591) — LayoutReader (Microsoft), fetched.

- LayoutReader is the standard reference for **reading-order-as-a-learned-task**, built on **ReadingBank**: 500,000 document images with reading order, text, and layout, auto-annotated by extracting Word document XML structure (which encodes true reading order) and rendering to PDF/image — a clever "ground truth for free from the source format" trick. **[UNVERIFIED]** the fetch did not surface LayoutReader's specific evaluation metrics (the abstract text available did not name BLEU/ARD/Kendall-tau explicitly, only stating the model "performs almost perfectly"). From general domain knowledge **[UNVERIFIED]**: reading-order evaluation in the broader literature commonly uses (a) **BLEU over the sequence of block IDs** (treating reading order as a sequence-generation task and scoring n-gram overlap of the predicted order against ground truth), (b) **Average Relative Distance / normalized Kendall-tau distance** between predicted and true permutations (counting pairwise order inversions, normalized by the maximum possible number of inversions for n elements — i.e., essentially Kendall's tau rank-correlation reframed as a distance/error metric), and (c) plain **edit distance** over the block-ID sequence (as OmniDocBench uses, A.1). **Recommendation:** since OmniDocBench's reading-order metric (edit distance on block sequence, independently confirmed via fetch in A.1) is already a de facto standard with published baselines, OpenConvert should adopt **normalized sequence edit distance on block/paragraph IDs** as its primary reading-order metric, and optionally add **Kendall-tau distance** as a secondary "how locally scrambled is it" signal, since edit distance and Kendall-tau penalize different failure shapes (edit distance is harsher on insertions/deletions of whole blocks; Kendall-tau is a purer "did we get relative order right" signal when the block set itself is correct — useful for isolating pure reading-order bugs from content-loss bugs).

### A.13 Footnote linking evaluation

**[UNVERIFIED]** — No dedicated, named public benchmark for footnote-to-reference linking accuracy was found or fetched this session; this appears to be a genuine gap in the public benchmark landscape (footnotes are typically evaluated only implicitly, as part of a broader reading-order or text-extraction score, not as a standalone task with its own metric). **Recommendation:** treat footnote linking as a **precision/recall pair extraction problem** — evaluate it the same way relation-extraction/entity-linking tasks are evaluated in NLP: for each footnote marker in the body text, is there a correctly-linked footnote body (exact match on the (marker-location, footnote-id) pair)? Report as Precision = correct links / predicted links, Recall = correct links / ground-truth links, F1 = harmonic mean — standard IE-style scoring, with no external published baseline to calibrate against, so this metric's "good" threshold will have to be **self-calibrated against OpenConvert's own hand-labeled fixture corpus** rather than borrowed from a published number (mark any threshold here as internally-derived, not literature-derived).

### A.14 Table TEDS / TEDS-S

**Source:** [arxiv.org/pdf/1911.10683](https://arxiv.org/pdf/1911.10683) (PubTabNet paper, "Image-based table recognition: data, model, and evaluation" — Zhong et al.), fetched.

- **Exact formula (confirmed from source):**
  **TEDS(Ta, Tb) = 1 − EditDist(Ta, Tb) / max(|Ta|, |Tb|)**
  where Ta, Tb are the table's HTML structure represented as trees, EditDist is **tree-edit distance**, and |T| is the node count. Costs: insertion/deletion = 1; substituting a non-`<td>` node = 1; substituting two `<td>` cells with different colspan/rowspan = 1; substituting two structurally-matching `<td>` cells = **normalized Levenshtein similarity (0–1) of the cell text content** — i.e., TEDS blends *structural* tree-edit distance with *content* string-edit distance in one unified score, which is elegant but means a single TEDS number conflates "got the grid right" with "got the cell text right." **PubTabNet's own README/paper as fetched does not describe a formally separate "TEDS-S" (structure-only) variant** — this term is used informally in later papers (Table Transformer / Microsoft's work, and others) to mean TEDS computed with all cell-content substitution costs fixed at a constant (i.e., ignoring text-content correctness and only scoring the grid/merge structure). **[UNVERIFIED]** the exact TEDS-S formal definition/origin paper, but its construction (freeze the content-similarity term) follows directly from the TEDS formula above, so OpenConvert can implement it correctly even without a separate citation: **TEDS-S = TEDS with cell-substitution cost fixed to a constant (e.g., always 0 for matching structure, ignoring content), used to isolate table-structure detection from text-extraction accuracy.**
- **Baseline results (fetched, PubTabNet test set):** EDD (the paper's proposed model) 88.3% average TEDS (91.2% simple / 85.4% complex tables); WYGIWYS 78.6%; Adobe Acrobat (image-based) 53.7%; Camelot 73.0%; Tabula 67.9%. These 2019-era numbers are now old (2024–2025 tools like Docling's TableFormer and MinerU report TEDS in the low-to-mid 90s on OmniDocBench-style leaderboards per A.1/A.2), but they usefully bound the *low end*: classical rule-based table extractors (Camelot, Tabula) land **68–73% TEDS**, giving OpenConvert a concrete "below this, a table extraction approach is not competitive" floor if it ever falls back to a similarly naive table heuristic.

### A.15 EPUB-specific quality measures

**Sources:** [w3.org/publishing/epubcheck/](https://www.w3.org/publishing/epubcheck/), [daisy.org Ace docs](https://daisy.org/guidance/tools/ace/) (fetched with partial success), [github.com/daisy/ace](https://github.com/daisy/ace) (404 on this exact path this session — repo may have moved/renamed; **[UNCONFIRMED-LOOKUP]** on exact current URL), [w3.org/TR/epub-a11y-11/](https://www.w3.org/TR/epub-a11y-11/)

- **EPUBCheck:** the official conformance checker for EPUB 2/3 (maintained under the W3C/DAISY/Adobe/Google/etc. consortium umbrella). Binary-ish pass/fail model: a clean run reports **"No errors or warnings detected!"**; otherwise it emits categorized **Errors** (spec violations — fail conformance) and **Warnings** (non-critical issues) with a **Messages Reference** for interpreting each code. **Recommendation for OpenConvert CI:** treat **EPUBCheck error count = 0** as a hard release gate (not just a warning-level metric) — this is binary and unambiguous, unlike similarity-based text metrics, so it belongs in the "fast unit tier" (§B.9) as a fixture-level assertion, not just a nightly aggregate stat. Warning count can be tracked as a trend metric (§D.5) without gating.
- **Ace by DAISY:** automated EPUB **accessibility** checker, built on the **axe-core** engine (Deque Systems' widely-used open-source accessibility testing engine — same engine used across the web-a11y-testing ecosystem, e.g. Playwright/axe integrations). Explicitly self-described as only covering "a limited portion" of accessibility checks — i.e., a helper for a human-driven review, not a complete substitute (directly analogous to how EPUBCheck validates conformance but not "good" EPUBs). ### A.16 Recommended metric suite for OpenConvert (with literature-anchored thresholds)

Given the above, a concrete, non-invented metric suite:

| Stage | Metric | Formula / method | "Good" threshold anchor (from published numbers above) |
|---|---|---|---|

| Footnote linking | Precision/Recall/F1 on (marker, footnote-id) pairs (A.13, self-defined) | standard IE-style P/R/F1 | no external baseline; self-calibrate |

This three-tier structure mirrors what Marker itself does in practice (heuristic pass/fail as primary, LLM-judge/composite scores as secondary) and is the single strongest piece of precedent found in this research.

## Part B — Testing strategy patterns for pipelines like this

### B.1 Golden/snapshot testing of intermediate representations

**Sources:** [insta.rs/docs](https://insta.rs/docs/) (Rust), [github.com/tophat/syrupy](https://github.com/tophat/syrupy) (Python), [vitest.dev/guide/snapshot.html](https://vitest.dev/guide/snapshot.html) (JS) — all fetched.

- **insta (Rust):** provides **redactions** and **snapshot string filtering** specifically to strip/replace volatile data before comparison, multiple serializer/snapshot-type options, and a documented file format so snapshots are diffable in code review. Maintained by Armin Ronacher; has a VS Code extension for fast accept/reject review.
- **syrupy (Python/pytest):** stores snapshots in `.ambr` ("Amber") files under `__snapshots__/`, explicitly instructs committing that directory to version control, and **normalizes line endings (`\r`/`\n` → `\n`)** at snapshot-write time specifically for cross-platform stability — directly relevant to OpenConvert's Win/macOS/Linux CI matrix (§B.10). Supports `exclude`/`include` filters and `path_type()` matchers to replace volatile values (timestamps, IDs) by type rather than exact value, plus custom extensions including a `JSONSnapshotExtension` (useful for a canonical-JSON-IR snapshot strategy) and image-snapshot extensions (PNG/SVG) that could double as a lightweight visual-diff mechanism without a full Playwright setup for small internal component checks.
- **Vitest (JS/TS):** three snapshot modes — file snapshot (`toMatchSnapshot`), inline snapshot (`toMatchInlineSnapshot`, embeds the expected value directly in the test source — good for tiny, highly-reviewable assertions since the diff shows up as a normal code diff), and `toMatchFileSnapshot` (compares against a standalone file with a custom extension, preserving syntax highlighting and avoiding string-escaping noise — well suited to snapshotting generated XHTML/OPF/NCX files directly as `.xhtml`/`.opf` fixtures rather than escaped strings inside a `.snap` file). Explicitly recommends **custom serializers** (`expect.addSnapshotSerializer`) to control exactly what gets written.

**Cross-language synthesis for OpenConvert's canonical-JSON-IR strategy** (this is the concrete recommendation the user's Part B ask is pointing at):
1. **Sort object keys** before serialization (all three ecosystems support this via custom serializers/matchers) so diffs are stable regardless of insertion order.
2. **Round floats** to a fixed precision (e.g., bounding-box coordinates to 2 decimal places) before snapshotting — unstated in any single fetched source but a direct, necessary consequence of the float-determinism concerns raised across all three tools' "redaction/filter" features, and standard practice wherever float output is snapshotted.
3. **Normalize line endings** at snapshot-write time (syrupy does this by default; insta/vitest should be configured to match) — critical for the Win/macOS/Linux matrix (§B.10).
4. **Redact/exclude genuinely volatile fields** (timestamps, generated UUIDs, absolute file paths) rather than trying to make them deterministic — all three tools support this natively; don't fight it by mocking clocks everywhere.
5. **Commit snapshots to version control and require human review on diff** — universal guidance across all three tools' docs; snapshot-diff review is explicitly part of the code-review process, not an auto-approve step.
6. Prefer **file-based snapshots with real extensions** (`.xhtml`, `.opf`, `.json`) over string-escaped inline snapshots for OpenConvert's IR, since the IR documents are large structured artifacts, not short values — this matches Vitest's `toMatchFileSnapshot` guidance and syrupy's single-file extensions.

### B.2 Fixture-based tests with tiny hand-made PDFs

Not separately covered by a single fetched source, but directly supported by the olmOCR-bench pattern (A.5) and general TDD practice: build a library of **minimal, hand-crafted PDFs**, each isolating exactly one pipeline concern — a single rotated page, a single multi-column layout, a single table with merged cells, a single footnote, a single ligature (e.g., "ﬁ"/"ﬂ"), a single hyphenated word broken across a line, a single embedded/subset font, a single RTL-text page, a single malformed/edge-case PDF (missing xref table, encrypted-but-no-password, etc.). Each fixture should ship with **explicit fact assertions** (olmOCR-bench-style, A.5) rather than only a snapshot diff, since assertions survive intentional, benign IR changes (e.g., refactoring field names) that would otherwise break a naive snapshot test. **[UNVERIFIED]** no single canonical "how to build a minimal PDF test corpus" guide was fetched this session; this recommendation synthesizes A.5's assertion pattern with standard fixture-testing practice.

### B.3 Property-based testing

**Sources:** [hypothesis.readthedocs.io](https://hypothesis.readthedocs.io/en/latest/) (Python), [github.com/proptest-rs/proptest](https://github.com/proptest-rs/proptest) (Rust), [github.com/dubzzz/fast-check](https://github.com/dubzzz/fast-check) (JS/TS) — all fetched.

All three libraries share the same core model: declare `@given`/strategy-driven properties that must hold for *all* generated inputs in a described range, and the framework **shrinks** any failing case down to a minimal reproducer automatically. proptest's docs give a worked date-parser example showing shrinking converging from `2497-08-27` down to `0000-10-01` as the minimal failing input — a good illustration of why property tests catch edge cases fixture tests miss, without requiring the author to have thought of that exact case.

**Concrete properties recommended for OpenConvert's text-extraction/reflow layer** (synthesizing the frameworks' own stated use-cases — parser robustness/validity/correctness patterns from proptest's docs, and fast-check's explicit metamorphic-testing example):
- **Idempotence:** re-running the reflow/normalization stage on its own output should be a no-op (`normalize(normalize(x)) == normalize(x)`) — directly matches proptest's "round-trip" pattern.
- **No text loss (set containment, order-insensitive):** the multiset of normalized words extracted from the source PDF should be a **subset** (modulo Unicode normalization, hyphenation-rejoining, and ligature expansion) of the multiset of words present in the produced EPUB's text content — this is exactly the kind of property proptest/hypothesis/fast-check are built for, since "no text loss" is a relational property across two representations of arbitrary generated documents, not a single fixed expected value.
- **Monotonic reading order within a column:** for any synthetically generated single-column page (property-generated block positions), extracted block order should be monotonically increasing in the vertical (and secondarily horizontal) axis — a property, not a golden value, since it should hold for *any* valid single-column layout, not just hand-picked ones.
- **Robustness/no-crash:** the parser should never panic/throw on arbitrary byte input (fast-check/proptest's "robustness" pattern applied to malformed-PDF fuzzing) — this overlaps with mutation/fuzz testing (§B.7) but is naturally expressed as a property test with `fc.string()`/`prop::collection::vec(any::<u8>(), ..)`-style raw-byte generators.

fast-check's own docs explicitly demonstrate a **metamorphic** double-reversal example (`reverseText(reverseText(x)) === x`) as one of its canonical patterns — directly bridging property-based testing and metamorphic testing (§B.4); the two are complementary, not competing, techniques and OpenConvert should use both.

### B.4 Metamorphic testing

**Source:** [en.wikipedia.org/wiki/Metamorphic_testing](https://en.wikipedia.org/wiki/Metamorphic_testing) (fetched); seminal citations confirmed: **Chen et al. (1998)**, "Metamorphic testing: A new approach for generating next test cases" (HKUST tech report — the originating paper); **Segura et al. (2016)**, "A survey on metamorphic testing," *IEEE TSE* 42(9):805–824 (the standard survey to cite). A cited application example: **Lidbury et al. (2015)**, "Many-core compiler fuzzing," using MT for compiler verification — establishing precedent for MT on complex, hard-to-oracle software systems (compilers), directly analogous to a PDF-parsing pipeline where "correct output" for an arbitrary real-world PDF has no independently-known ground truth.

**Concrete metamorphic relations for OpenConvert** (per the user's brief, elaborated against the confirmed MT definition — "necessary properties of the intended functionality... involving multiple executions"):
- **Page-order invariance:** given a synthetic multi-page PDF, permuting the page order (a controlled source transformation) and re-running the pipeline should yield the same *per-page* text content, correspondingly permuted — i.e., `extract(permute_pages(doc)) == permute(extract(doc))`.
- **Rotation invariance:** rotating a page 0/90/180/270 degrees (adjusting the page's `/Rotate` attribute, a metadata-only change on a synthetic fixture) should yield identical extracted text content (not necessarily identical bounding boxes, but identical reading-order text sequence).
- **Content-stream reordering invariance:** shuffling the order of drawing operators *within a single text line* in a hand-crafted PDF's content stream (while keeping visual positions fixed) must not change extracted text — this directly targets a common real-world PDF-generator quirk (many PDF producers emit glyphs out of visual order) and is exactly the kind of relation that's cheap to generate synthetically (generate N random valid orderings of the same operator set) but impossible to hand-author exhaustively as fixtures.
- These are ideal for a **synthetic corpus generator**: write a small PDF-content-stream builder (not a full PDF library dependency) that emits controlled variations and asserts the metamorphic relation holds across all variations — this is cheap, fast-tier-appropriate (no external oracle needed, unlike differential testing §B.5), and catches an entire class of "should be invariant but isn't" bugs that neither snapshot tests nor property tests targeting a single execution would find.

### B.5 Differential testing against reference-tool oracles

Not covered by a dedicated fetched source this session, but well-established practice and directly implied by OmniDocBench/docling-eval's own "compare against ground truth" pattern generalized to "ground truth for text coverage = union of what independent tools extract." **[UNVERIFIED specifics, standard practice]**: use **`pdftotext`** (Poppler, widely available, BSD/GPL-family license, deterministic, no ML) and **Calibre's** `ebook-convert`/internal PDF-text extraction as **independent oracles for raw text coverage** (not structure/reading-order, where they're weak) — i.e., the property to test is "every word `pdftotext` extracts from this PDF should also appear somewhere in OpenConvert's EPUB output (modulo normalization)," which is a differential/oracle-based instantiation of the same "no text loss" property from §B.3, but validated against an independent, mature implementation rather than only against OpenConvert's own fixtures — catching bugs that are invisible to self-authored fixtures/snapshots because the bug and the fixture's expected value were authored by the same (mistaken) mental model. This should run at the **integration tier** (§B.9), not fast-unit, since it requires shelling out to external binaries.

### B.6 Regression suites keyed by corpus file + sha256

**[UNVERIFIED]** no single fetched source, but this is standard practice directly supported by the snapshot tools above (all three snapshot libraries key files by test name, which should itself encode/be paired with the fixture's content hash). **Recommendation:** name/key each regression-suite entry by `(source_filename, sha256(source_bytes))`, not just filename — this (a) makes silent fixture corruption/edits immediately visible (hash mismatch = fixture changed, requiring explicit re-baseline, not a silent drift), (b) allows safely vendoring third-party corpus subsets (e.g., a licensed OmniDocBench/olmOCR-bench slice, A.1/A.5) with provenance tracking, and (c) supports content-addressed caching of expensive pipeline runs in CI (skip re-running a stage if the input hash and pipeline-version hash both match a cached result) — directly useful for the nightly-full-corpus tier's cost (§B.9).

### B.7 Mutation testing

**Sources:** [mutmut.readthedocs.io](https://mutmut.readthedocs.io/en/latest/) (Python, fetched fully), [mutants.rs](https://mutants.rs/) (cargo-mutants, Rust — fetched but landing page only, limited detail).

- **mutmut (Python):** workflow is `mutmut run` (generate + test mutants) → `mutmut browse` (interactive TUI to inspect survivors) → write tests to kill survivors → `mutmut apply`. Confirmed mutation operators include integer-literal increment (`0→1`, `5→6`), comparison-operator flips (`<`→`<=`), and control-flow swaps (`break`↔`continue`) — the docs explicitly state mutations should be **"as subtle as possible"** to maximize their power to reveal real test gaps (a loud, obviously-wrong mutant that any test trivially catches is a wasted mutant). **Mutation score** = percentage of generated mutants killed (caught) by the test suite; exportable as a Shields.io-compatible badge (`mutmut badge`) and CI stats (`mutmut export-cicd-stats`); supports incremental runs (remembers prior results, doesn't require full re-run each time) — directly relevant for keeping mutation testing affordable enough to run regularly rather than only pre-release.
- **cargo-mutants (Rust):** confirmed to exist and to be "easy to run on any Rust source tree" with a one-command (`cargo mutants`) workflow, explicitly designed to surface areas where "bugs might be lurking or tests might be insufficient." **[UNVERIFIED]** specific mutation operators and CI-integration mechanics for cargo-mutants — the landing-page fetch didn't surface this level of detail; recommend a follow-up fetch of `github.com/sourcefrog/cargo-mutants`'s README/docs before writing implementation-level guidance.
- **Recommendation for OpenConvert:** given the described architecture likely spans Rust (deterministic pipeline core, per the `insta`/`proptest` mentions in the brief) and Python (LLM adapter / eval tooling, per `hypothesis`/`syrupy` mentions), run **both** cargo-mutants (Rust core) and mutmut (Python glue/eval code) — but only in the **nightly tier** (§B.9), not per-PR, since mutation testing is inherently slow (runs the full test suite once per mutant, and a non-trivial pipeline codebase can generate hundreds to thousands of mutants). Track mutation score as a **trend metric**, not a hard gate initially — set a floor only after establishing a baseline, consistent with how OmniDocBench-style thresholds should be self-calibrated (§A.16) rather than picked arbitrarily.

### B.8 Contract tests for the LLM adapter

Directly supported by the JSON Schema material (§C.1) — the LLM adapter's contract should be tested exactly like any other typed API boundary: **given a fixed, hand-authored prompt/input, assert the response validates against a JSON Schema**, independent of whether the response content itself is "good" (that's a separate semantic-assertion/golden-decision concern, §C.2/C.5). This is squarely a **fast-unit-tier** test (§B.9) once combined with cassette-replay (§C.4) to avoid a live model call — schema validation is cheap and deterministic even though the underlying model call is not.

### B.10 CI matrix (Windows / macOS / Linux)

Not covered by a dedicated fetched source, but directly required by two confirmed facts above: (a) Playwright's own docs explicitly warn that **"browser rendering can vary based on host OS, version, settings, hardware, power source"** and require **separate baseline screenshots per OS/browser combination** (filenames literally embed the platform, e.g. `...-chromium-darwin.png`, confirmed fetch, §D.1); (b) syrupy explicitly normalizes line-endings specifically because of cross-platform `\r`/`\n` divergence (confirmed fetch, §B.1). **Recommendation:** run the fast-unit and integration tiers on all three OSes on every PR (these tiers should be OS-*insensitive* by construction — text/IR snapshots normalized per B.1, no visual pixel comparison at this tier); run the nightly tier's **visual regression** sub-suite with **per-OS baseline images** (not shared baselines) exactly per Playwright's documented pattern, since font rendering (subpixel hinting, hinting algorithm differences between FreeType/Linux, Core Text/macOS, DirectWrite/Windows) is a genuine, unavoidable source of pixel-level non-determinism across OSes that no amount of "fixing the code" resolves — it must be handled at the baseline-management level (§D.4), not chased away.

### B.11 Test determinism (float rounding, font rendering)

Synthesized from B.1 (snapshot float-rounding guidance) and D.1/D.4 (Playwright's explicit OS-rendering-variance warning): **two distinct kinds of non-determinism require two distinct mitigations** — (1) **numeric non-determinism** (bounding-box floats, confidence scores, timing-dependent values) is mitigated by **rounding before snapshotting** and **excluding genuinely non-reproducible fields** (timestamps) via the snapshot tools' native redaction features (B.1); (2) **rendering non-determinism** (pixel-level font-rasterization differences across OS/GPU) cannot be "fixed" the same way — it requires either **bundling a fixed font + fixed rendering path** (e.g., render via a headless, OS-independent rasterizer rather than relying on OS text-shaping) to make pixel comparison meaningful at all, **or** abandoning pixel comparison in favor of **structural DOM/content assertions** (Playwright's own docs mention ARIA/accessibility-tree snapshots as an explicit alternative to pixel screenshots for exactly this reason) wherever the check doesn't genuinely need to be pixel-level (see §D.4 for the full mitigation menu).

## Part C — Testing LLM-assisted steps deterministically

### C.1 Structured output + JSON-schema validation

**Source:** [json-schema.org](https://json-schema.org/) (fetched, general overview only — vendor-specific structured-output docs, e.g. OpenAI/llama.cpp grammar-constrained decoding, were not separately fetched this session, **[UNVERIFIED]** implementation specifics for any one provider). The core pattern is well-established: constrain the LLM's output to a fixed JSON Schema (via grammar-constrained decoding where the local runtime supports it — llama.cpp supports GBNF grammars for exactly this purpose, **[UNVERIFIED]** exact current API surface, not fetched this session) and **validate every response against that schema before it's allowed to affect the pipeline**, independent of whether the response content is semantically good. This is the first, cheapest line of defense and should be a **hard, unconditional gate** — any schema-invalid response is a pipeline error, not a "low quality" result, and should trigger fallback to the deterministic-only path rather than being passed through.

### C.2 Semantic assertions (beyond schema validity)

Directly per the user's brief and consistent with olmOCR-bench's assertion philosophy (A.5) and Grobid's field-level-F1 pattern (A.8) — schema validity alone doesn't mean the LLM's decision was sound. Concrete semantic assertions for a document-repair LLM step:
- **Permutation invariant:** "returned block IDs are a permutation of input block IDs" (no IDs invented, none dropped) — a pure set-equality check, cheap and unconditional.
- **Monotonicity:** "heading levels are monotonic" (e.g., never jump from H1 directly to H4 without an intervening H2/H3, or whatever the specific structural rule is) — a simple sequence-property check.
- **Closed-label-set membership:** "labels ∈ allowed set" (e.g., classification/repair-action labels must be from a fixed enum) — this overlaps with schema validation (C.1) if the schema itself uses an enum type, but is worth asserting independently as a defense-in-depth measure against schema-bypass bugs.
These are exactly the kind of properties **property-based testing frameworks (§B.3) are built to check**, applied specifically to the LLM adapter's *output shape*, decoupled from output *content quality* (which is the golden-decision/calibration concern, §C.5/C.9).

### C.3 Fixed-seed / temperature-0 determinism limits (llama.cpp)

**[UNVERIFIED]** — direct attempts to fetch llama.cpp GitHub issues/discussions specifically about determinism returned 404s this session (the specific issue/discussion numbers guessed were wrong; a targeted search would be needed to find the live thread, but WebSearch quota was exhausted). This is reported here from **general domain knowledge, not session-verified**, and should be flagged for follow-up verification: **greedy decoding (temperature 0) with llama.cpp is *not* guaranteed to be bit-reproducible across different thread counts or CPU backends**, because matrix-multiplication reduction order (and thus floating-point rounding) depends on how work is partitioned across threads/SIMD lanes, and floating-point addition is not associative — different thread counts change the summation order of the same mathematical dot-product, which changes the last few bits of the result, which can (rarely but non-zero-probability, especially near a logit tie) flip which token has the highest logit, cascading into a different generated token and thus a different subsequent generation trajectory. **The practical implication for OpenConvert is significant and should shape the architecture**: do **not** assume "temperature 0 + fixed seed" gives bit-for-bit reproducibility across different machines/thread-count configurations, even though it substantially reduces (but does not eliminate) variance compared to sampling with temperature > 0. **Recommendation:** (a) pin the thread count used for any LLM-repair call to a fixed value in CI/test environments specifically to make cassette-recorded outputs reproducible *on that fixed configuration* (§C.4), (b) never assert exact-string-match on live (non-cassette) LLM output in tests — always assert against schema/semantic properties (§C.1/C.2) or cassette-replayed fixed strings, and (c) treat any single LLM call's output as a **sample**, not a **deterministic function of input**, for testing-architecture purposes, even under temperature 0 — this is the single most important framing point for Part C and should be stated explicitly in any architecture doc: "temperature 0 reduces variance, it does not guarantee determinism across hardware/thread configurations." ### C.4 Recording/replay ("VCR"-style cassettes) for LLM calls

**Sources:** [github.com/vcr/vcr](https://github.com/vcr/vcr) (Ruby, the originating library, fetched), [pypi.org/project/vcrpy](https://pypi.org/project/vcrpy/) (Python port, fetched).

Both confirm the **cassette** pattern: first test run makes a real HTTP call and serializes request+response to a file (YAML by default); subsequent runs intercept matching requests and replay the recorded response instead of hitting the network — explicitly advertised as delivering **"fast, deterministic, accurate tests"** and enabling **offline** test execution. This is directly and cleanly applicable to LLM-adapter testing: **treat the local LLM runtime's API surface as "the network call" that VCR-style tooling wraps.** Concrete design, synthesizing the user's brief with the VCR/vcrpy pattern:
- **Cassette key = hash(prompt text + model id + prompt-template version + relevant generation params)** — not just the raw prompt string, since the same prompt text run against a different model or a bumped prompt-template version should **not** silently replay a stale cassette (this is the LLM-specific refinement VCR's own matching-by-request-body model doesn't natively express, since VCR matches HTTP requests, not "logical prompt identity" — vcrpy's own docs note matching is configurable by request body/headers, which maps onto this but needs the OpenConvert-specific key fields added explicitly).
- **Fast-unit and integration tiers (§B.9) run exclusively against cassettes** — never invoke a real model in these tiers, matching VCR's core "deterministic tests" value proposition directly.
- **Nightly tier is the only place cassettes get (re-)recorded**, and re-recording should be an explicit, reviewed action (a cassette diff is a meaningful code-review artifact — "the model's behavior for this exact prompt changed" is worth a human look, directly analogous to how snapshot-diff review works in §B.1) — this connects cassette management to the same "commit + review diffs" discipline established for IR snapshots.
- A **prompt-version bump should be treated as invalidating all cassettes keyed to the old version**, forcing deliberate re-recording rather than accidental staleness — this is the mechanism that makes "canary tests for prompt regressions" (user's brief, §C's canary-test ask) actually work: a canary test is simply a fixed, small set of cassette-backed test cases that must continue to produce the *same schema-valid, semantically-assertion-passing* output across prompt-template revisions; a canary "failure" is either an intentional cassette re-record (reviewed, expected) or an unreviewed regression (caught by CI).

### C.5 "Golden decision" tests with accuracy threshold instead of exact match

Directly per the user's brief, and consistent with the calibration/selective-prediction literature synthesized in §C.9/C.10: for genuinely judgment-based LLM decisions (e.g., "should this ambiguous line be a heading or emphasized body text?"), exact-match testing is inappropriate because reasonable humans/models can differ on edge cases. Instead: maintain a **human-labeled golden set** (a curated sample of real, hard cases with an agreed-upon correct label) and assert the LLM adapter's **aggregate accuracy on this set stays at or above a threshold**, not that each individual case matches exactly. This directly parallels the standard ML-evaluation practice of tracking accuracy/F1 against a held-out labeled set rather than requiring bit-exact output — the same practice underlying every benchmark in Part A. **Threshold-setting guidance:** set the initial threshold at the **measured baseline accuracy minus one margin-of-error** (mirroring olmOCR-bench's own practice of reporting scores with explicit ± confidence intervals, A.5) so the gate is statistically meaningful rather than an arbitrary round number — e.g., if the golden set yields 91% ± 3% on first measurement, gate at ~88%, not at a guessed "90%."

### C.6 Canary tests for prompt regressions

Covered above as a direct consequence of the cassette-versioning design (§C.4): a canary suite is a small, fixed, cassette-backed set of prompt/input pairs whose **schema validity + semantic-assertion pass rate** (§C.1/C.2) must remain stable across prompt-template edits. Distinct from golden-decision tests (§C.5, which measure *accuracy against human labels*) — canaries measure *stability of behavior shape*, catching e.g. "the model started wrapping JSON in markdown code fences" or "the model started including a preamble sentence before the JSON" — structural regressions that break parsing even when the underlying judgment quality hasn't changed.

### C.7 Paired comparison: did the LLM improve over deterministic-only?

**Source:** [en.wikipedia.org/wiki/McNemar%27s_test](https://en.wikipedia.org/wiki/McNemar%27s_test) (fetched, formula confirmed); Berg-Kirkpatrick et al. 2012 confirmed to exist at [aclanthology.org/D12-1091](https://aclanthology.org/D12-1091/) (the standard NLP reference for bootstrap significance testing) but abstract/methodology detail **[UNVERIFIED]** — the fetch returned only bibliographic metadata, not the paper's substantive recommendations, so its specific guidance (e.g., recommended bootstrap sample counts) could not be confirmed this session.

- **McNemar's test formula (confirmed):** χ² = (b − c)² / (b + c), where *b* = cases where system A passes and system B fails, *c* = cases where A fails and B passes (the concordant cases — both pass or both fail — are excluded, since McNemar's test is specifically about **paired, discordant outcomes**). This is exactly the right test for "did adding the LLM-repair step change the pass/fail outcome on the olmOCR-bench-style assertion suite (§A.5/§A.16), file by file" — run the deterministic-only pipeline and the deterministic+LLM-repair pipeline over the **same** corpus, tabulate the 2×2 (both pass / both fail / A-only-pass / B-only-pass), and apply McNemar's test to determine whether the LLM step's net effect is statistically significant rather than noise, at the corpus size OpenConvert can practically maintain (McNemar's chi-squared approximation requires b+c ≥ 25 for validity per the fetched Wikipedia summary; for smaller discordant-pair counts, the exact binomial form of McNemar's test should be used instead — a detail worth flagging for implementation).
- **Bootstrap confidence intervals** (general NLP-evaluation practice, per Berg-Kirkpatrick et al.'s well-known role in the field, **[UNVERIFIED exact methodology from this session's fetch]**): resample the corpus with replacement N times (commonly 1,000–10,000 resamples in NLP practice), recompute the aggregate metric (e.g., composite score, §A.16) on each resample, and report the resulting empirical distribution's 95% interval — this gives OpenConvert a **corpus-size-aware** sense of whether an observed score change (e.g., 82% → 84% after an LLM-repair step) is likely to be real or just corpus-composition noise, which matters especially at the ~20-file integration-tier corpus size (§B.9) where naive point-estimate comparisons would be unreliable.

### C.8 Measuring false-repair rate (the key risk)

Not covered by a single dedicated fetched source — this is a genuine literature gap similarly noted for footnote-linking (A.13) — but directly derivable from the paired-comparison design in §C.7: **false-repair rate = the fraction of (assertion, file) pairs where the deterministic-only pipeline passed and the LLM-repair-augmented pipeline failed** — i.e., exactly the "*c*" quantity in McNemar's 2×2 table (§C.7), reframed as a rate rather than a raw count, and tracked **as its own first-class metric, separately from net accuracy change**, because a net-positive McNemar result can still hide a concerning false-repair rate if the LLM's *gains* happen to outweigh its *harms* on the current corpus but the harms are individually severe (e.g., silently corrupting a correct table into an incorrect one is a worse failure mode than failing to fix a broken heading, even if both count as "one assertion flip" in a naive aggregate). **Recommendation:** report false-repair rate **per assertion-category** (mirroring olmOCR-bench's 8-category breakdown, A.5), not only in aggregate, and treat any category with a false-repair rate above a small fixed ceiling (e.g., a few percent — a number that should be set from the corpus's own measured baseline variance per §C.5's margin-of-error approach, not guessed) as disqualifying for that category regardless of net-positive aggregate accuracy — this is the direct, concrete TDD-flavored answer to "how do you test that the LLM step is actually safe to ship," and is the single most important Part C deliverable given the user's explicit framing of false-repair as "the key risk."

### C.9 Confidence calibration: is the confidence score meaningful?

**Sources:** [arxiv.org/abs/1706.04599](https://arxiv.org/abs/1706.04599) (Guo et al. 2017, "On Calibration of Modern Neural Networks" — fetched); [arxiv.org/abs/1904.01685](https://arxiv.org/abs/1904.01685) (Nixon et al. 2019, "Measuring Calibration in Deep Learning" — fetched, and importantly this paper **critiques** naive ECE); Naeini et al. 2015 ("Obtaining Well Calibrated Probabilities Using Bayesian Binning into Quantiles," AAAI — confirmed to exist and be the originating BBQ-calibration/ECE-adjacent paper via fetch, but full formula not retrieved this session, **[UNVERIFIED exact ECE formula from a live 2026 fetch]**).

- **Guo et al. (confirmed):** modern (post-2016-era) neural networks are frequently **poorly calibrated** despite being more accurate than older, better-calibrated networks — i.e., **raw softmax/logit confidence should not be trusted as a probability without post-hoc calibration**, a finding directly relevant to any deterministic-pipeline "confidence heuristic score" OpenConvert might compute (rule-based confidence scores are not automatically well-calibrated just because they're deterministic — they need the same empirical validation as a model's softmax output). **Temperature scaling** (a single learned scalar dividing the logits before softmax) is reported as "surprisingly effective" — the simplest possible calibration fix, worth trying first before anything more complex.
- **Nixon et al. (confirmed):** a useful, more recent corrective — **naive ECE has "numerous flaws"** (binning-strategy sensitivity, threshold sensitivity, choice of L1 vs L2 norm, whether to condition per-class). **Recommendation for OpenConvert:** don't treat a single ECE number as a solved, unimpeachable metric; use **adaptive binning** (not fixed-width bins) and report **class-conditioned** calibration where the confidence score gates a multi-class decision (e.g., "which repair action to take"), per Nixon et al.'s stated recommendations.
- **ECE definition [UNVERIFIED exact formula this session, standard/high-confidence from general knowledge]:** partition predictions into M confidence bins; **ECE = Σ_m (|B_m| / n) · |acc(B_m) − conf(B_m)|** — the weighted average absolute gap between each bin's empirical accuracy and its average predicted confidence. A **reliability diagram** plots accuracy vs. confidence per bin; a perfectly calibrated model traces the diagonal. This formula should be treated as high-confidence-but-not-session-verified and re-confirmed against Naeini et al. (2015) or Guo et al. (2017)'s full text before being published as an exact citation.
- **For OpenConvert's specific case — a deterministic heuristic confidence score, not a neural softmax:** the right validation procedure is (1) collect (confidence-score, was-the-repair-actually-correct) pairs on the labeled golden set (§C.5), (2) bin by confidence-score deciles, (3) plot the reliability diagram, (4) if it deviates from the diagonal, apply **isotonic regression** (a standard, assumption-light monotonic-calibration technique — well-established in ML practice, **[UNVERIFIED specific citation this session]**, commonly attributed to Zadrozny & Elkan's early-2000s calibration work) to remap the raw heuristic score onto empirically-accurate probabilities, or fall back to **simple threshold validation** (pick the threshold that empirically achieves the desired precision on the golden set, re-validated periodically as the corpus grows) if a full calibration curve isn't worth the engineering cost yet. **This directly answers the user's Part C calibration question**: yes, reliability diagrams + ECE (with Nixon et al.'s caveats) is the right validation tool, and isotonic regression is the right remediation when a deterministic heuristic's raw score isn't already well-calibrated — this is standard, transferable ML-evaluation practice, not something specific to neural confidence scores.

### C.10 Evidence that confidence-gated LLM usage (cascade/deferral) works

**Sources:** Madras, Pitassi & Zemel 2018 ("Predict Responsibly: Improving Fairness and Accuracy by Learning to Defer," NeurIPS 2018) — [arxiv.org/abs/1711.06664](https://arxiv.org/abs/1711.06664), fetched; Geifman & El-Yaniv ("Selective Classification for Deep Neural Networks") — fetched, confirming the **risk-coverage tradeoff** framing and a striking headline result: **2% top-5 ImageNet error at 99.9% confidence, achieved while still covering ~60% of test instances** by abstaining/deferring on the rest; **FrugalGPT** (Chen et al., cost-aware LLM cascading) — fetched, confirming **up to 98% cost reduction at matched accuracy, or +4% accuracy at matched cost**, via a *learned* routing/cascade policy across heterogeneous-cost LLMs.

- **The "learning to defer" framing (Madras et al., confirmed):** rather than forcing a system to always predict, let it output a **"Pass"** action that routes the decision downstream (to a human, or in OpenConvert's case, to the deterministic fallback / to a stricter secondary check) — and the paper's key result is that this **improves both accuracy and fairness simultaneously**, even when the downstream decision-maker is itself imperfect/biased. This is strong, directly-applicable precedent for OpenConvert's architecture: **the LLM-repair step should have an explicit "decline to repair, defer to deterministic output" action**, not just a binary "repair or don't," and the confidence-gating threshold is exactly the mechanism that triggers this deferral.
- **Selective classification / risk-coverage tradeoff (Geifman & El-Yaniv, confirmed):** the practical mechanism for **setting** a defer threshold is to pick a **target risk level** (e.g., "false-repair rate must stay under X%," directly connecting to §C.8) and then find the confidence threshold that achieves that risk **with a probabilistic guarantee**, accepting whatever coverage (fraction of cases where the LLM is allowed to act rather than deferring) results — i.e., **set the threshold from the risk target, not from an arbitrary confidence-score cutoff**, and expect coverage (how often the LLM gets to help at all) to be the free variable that falls out, not something to fix in advance.
- **Cascades specifically for cost/latency (FrugalGPT, confirmed):** validates that a **learned, confidence-based routing policy** across a cascade of models of increasing capability/cost is a proven, published pattern for exactly OpenConvert's shape of problem (cheap deterministic pass first, escalate only when needed) — the magnitude of the reported gains (up to 98% cost reduction at matched accuracy) is strong evidence this architecture pattern is worth the added complexity, not just a theoretical nicety.
- **Synthesis / concrete recommendation for OpenConvert:** (1) compute a calibrated confidence score for "is deterministic-only output already good enough" (§C.9's calibration procedure applies here too, symmetrically — not just to the LLM's own decisions); (2) set the **escalate-to-LLM threshold** using the selective-prediction risk-coverage method (Geifman & El-Yaniv) against a **false-repair-rate risk target** (§C.8), validated on the golden set (§C.5); (3) give the LLM step itself an explicit **defer/decline** action per the learning-to-defer framing (Madras et al.), so a low-confidence LLM output doesn't get force-applied just because the LLM was invoked; (4) treat the resulting three-tier cascade (deterministic → LLM-repair → decline/flag-for-human) the same way FrugalGPT frames its model cascade — as a **learned/tuned routing policy validated against the corpus**, re-tuned as the corpus and models evolve, not a fixed threshold set once and forgotten.

### D.4 Cross-OS font-rendering nondeterminism mitigations

Synthesizing D.1 (Playwright's explicit OS-baseline-partitioning approach) and D.3 (BackstopJS's Docker-for-consistency approach), plus the user's brief's own suggested mitigation menu, ranked by robustness:

1. **Bundle a fixed font and control the rendering path end-to-end** (strongest fix, eliminates the root cause) — if OpenConvert's visual-QA harness renders EPUB content documents via a controlled, embedded rendering engine (e.g., a single pinned browser/rendering-library version bundled into the test environment, rather than relying on "whatever the OS's installed fonts + native text-shaping happen to be"), font-rendering variance across host OSes is eliminated at the source rather than tolerated after the fact. This is the BackstopJS Docker pattern generalized: **containerize/pin the rendering environment for any test that produces pixel output**, regardless of which comparison tool is used downstream.
2. **Disable antialiasing** for the specific purpose of pixel-exact comparison, where the test's goal is structural/layout correctness rather than actual visual-quality assessment — reduces (does not eliminate) sub-pixel hinting variance, a narrower/cheaper fix than #1.
3. **Per-OS baselines** (Playwright's own documented, first-party-recommended approach, confirmed §D.1) — accept that true cross-OS pixel identity isn't achievable without #1's containerization, and instead maintain separate accepted-baseline images per OS, gating each OS's CI run against its own baseline. Lower effort than #1, but multiplies the baseline-maintenance burden by the number of supported OSes (§B.10's three-OS matrix).
4. **Structural DOM/content assertions instead of pixel comparison** wherever the actual thing under test is layout/content-correctness rather than pixel-perfect rendering fidelity — Playwright's own docs explicitly mention **ARIA/accessibility-tree snapshots** as a first-party alternative to pixel screenshots for exactly this reason (confirmed §D.1's "structural alternatives" note). For OpenConvert specifically, this suggests a large fraction of "does the EPUB look right" checks can be done more robustly as **assertions on the rendered DOM** (element presence, text content, computed CSS box positions/order) rather than pixel screenshots — reserving true pixel-level visual regression for the smaller set of checks that are genuinely about visual fidelity (e.g., "does this embedded image render without distortion") where no structural proxy exists.

**Overall recommendation:** use structural DOM assertions (#4) as the default for the fast/integration tiers (cheap, OS-independent, no baseline-image maintenance burden at all); reserve pixel-level visual regression (via Playwright's native screenshot testing, §D.1, with per-OS baselines, #3, ideally running inside a pinned/containerized rendering environment per #1) for the nightly tier's genuinely visual-fidelity-focused checks only.

- **Peak RSS measurement, cross-platform:**
  - **Linux/macOS:** `/usr/bin/time -v` (GNU time). **Source:** [man7.org GNU time manpage](https://man7.org/linux/man-pages/man1/time.1.html), fetched — confirmed **`%M` = "Maximum resident set size of the process during its lifetime, in Kbytes"** is the exact, purpose-built field for this; also exposes `%t` (average RSS), `%K` (average total memory), `%D`/`%X` (average unshared data/shared text) as secondary signals.
  - **Cross-platform, in-process (Python-side tooling):** `psutil`. **Source:** [github.com/giampaolo/psutil](https://github.com/giampaolo/psutil), fetched — confirmed to expose `memory_info()` (returning `rss`, `vms`, `shared`, `text`, `data` fields) across Linux/Windows/macOS/BSD/Solaris/AIX. **[UNVERIFIED]** whether psutil exposes *peak* RSS directly as a single call (vs. requiring the caller to poll `memory_info().rss` repeatedly and track the max themselves) — the fetched README excerpt showed only the instantaneous-snapshot API, not a peak-tracking API; recommend either polling on an interval during the benchmark run (simple, portable, slight sampling-gap risk of missing a brief spike) or using OS-native peak-tracking where available (Linux's `/proc/[pid]/status` `VmHWM` field is the OS-native peak-RSS source `psutil` likely wraps internally — **[UNVERIFIED]**, general knowledge, not confirmed via fetch this session).
  - **Windows:** **Job Objects.** **Source:** [Microsoft Learn, Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), fetched — confirmed pattern: `CreateJobObject` → `AssignProcessToJobObject` (attach the process, or whole process tree, to the job) → run → `QueryInformationJobObject` (retrieve `JOBOBJECT_BASIC_ACCOUNTING_INFORMATION`/`...AND_IO_ACCOUNTING_INFORMATION` structures) to extract **aggregate peak memory across the entire process group** — explicitly the right tool when OpenConvert's pipeline spawns child processes (e.g., a separate LLM-runtime process) whose combined memory footprint needs to be measured as one figure, since Job Objects account for the whole tree, not just the top-level process (a capability plain `psutil`/GNU-time single-process measurement lacks unless manually summed across a known process tree).
  - **Recommendation:** for cross-platform harness consistency, build a thin wrapper that uses **Job Objects on Windows** and **`/usr/bin/time -v`'s `%M` (or direct `/proc/[pid]/status` `VmHWM` polling)** on Linux/macOS, normalizing both to a single "peak RSS in bytes, whole process tree" figure — this whole-tree framing matters specifically because OpenConvert's architecture (deterministic pipeline + local LLM runtime as likely-separate processes) means single-process memory measurement would understate real peak footprint.
- **Timing budgets:** directly informed by MinerU's own published quality/speed tradeoff data (§A.4 — "medium effort" costs 0.13 quality points for 35–220% speed gain) and Marker's per-mode throughput table (§A.3, 2.9 to 23.7 pages/sec across modes): **set per-tier timing budgets empirically from measured pipeline throughput on the corpus, not from a priori guesses**, and explicitly track quality-per-second as a joint metric (not quality and speed as independent, separately-optimized numbers) — since, per both A.3 and A.4's confirmed data, quality/speed is a **tunable tradeoff curve** in this problem domain, not two independent axes, the benchmark harness should report where OpenConvert sits on that curve at each configuration (fast/balanced/thorough, mirroring Marker's own mode naming, §A.3) rather than reporting a single quality number and a single speed number in isolation.
