## 1. OpenConvert's own license: Apache-2.0

D15 sets OpenConvert's license as **Apache-2.0**. The reasoning, laid out fully here because it is the single decision every other section in this document depends on:

**Why Apache-2.0 over MIT.** The dependency graph this project draws from includes several large, well-resourced patent holders — Google (PDFium), Microsoft (ONNX Runtime, Playwright), Meta (Llama, where used at all), NVIDIA (Nemotron). Apache-2.0's explicit patent grant and patent-retaliation clause give OpenConvert's contributors and users a symmetric patent grant from each other and strip patent rights from anyone who sues over the project — MIT is silent on both. Apache-2.0 is also already the license of the majority of the permissive half of this dependency landscape: PDFium's bindings, PDFBox, PdfPig (whose algorithms are ported — §6), Tesseract, Typst, most of the permissive-tier models. Choosing it is the license of least friction with the actual dependency graph, not an abstract preference (R8 Part C).

**Why not MPL-2.0.** MPL-2.0's file-level weak copyleft (the license Saxon-HE, bundled inside EPUBCheck, uses) is a reasonable middle ground in the abstract, but it does not buy OpenConvert the thing a copyleft license would actually buy — protection against a silent, whole-project proprietary fork. MPL's protection is per-file; a fork that adds proprietary code around unchanged MPL files stays fully compliant. It is the wrong tool for the fork-protection question this section addresses directly below.

**Why not GPL-3.0 — the Calibre precedent, both sides.** Calibre is GPL-3.0 and is the dominant open-source tool in exactly this space, which is real evidence that copyleft does not prevent a PDF/ebook tool from winning adoption — "GPL will kill adoption" is not a foregone conclusion for this category. Choosing GPL-3.0 would **not** block using PDFium (BSD-3 code can be pulled into a GPL project; the compatibility is one-directional but sufficient here). The actual cost of GPL-3.0 for OpenConvert is narrower and more strategic: it forecloses the "future commercial dual-license" option D15/R8 both flag as worth keeping open, since a GPL-3.0 project's own contributions would need either a CLA regime from day one (which D15 explicitly declines — DCO only, no CLA, §8 below) or a practically difficult later effort to track down every contributor for re-licensing consent.

**The fork-protection question, presented both ways, because DECISIONS.md asks it be weighed consciously rather than assumed.** The case *for* accepting permissive licensing's real cost (anyone can fork OpenConvert, add proprietary features, and compete without contributing back): it maximizes the contributor and integrator pool — organizations with blanket anti-copyleft policies can still use and contribute to OpenConvert; it keeps the future dual-license option open without a CLA; and precedent from adjacent categories (Chromium/Blink, VS Code — both largely permissive, both dominant despite being trivially forkable) suggests maintainer quality and community trust, not copyleft law, is what actually deters bad-faith forks for a healthy, actively maintained project of this shape. The case *for* GPL-3.0 instead: it is a legitimate, Calibre-precedented alternative that would not block PDFium, and its practical fork-deterrence value is real — it is just strongest for infrastructure/library code embedded invisibly inside other products, which is not quite this project's shape (a desktop end-user tool, not a library). On balance, given the project's own stated priority order — wide adoption first, fork-protection second, commercial optionality named as a live future possibility — **Apache-2.0 is the better fit**, but this is a real trade-off the Chief Architect is making deliberately, not a default that happened to be convenient.

**Why not AGPL-3.0.** AGPL's network-interaction disclosure trigger exists to close the SaaS loophole in GPL. OpenConvert is a local-first desktop app with no server component by design (D13.9) — AGPL would buy nothing over GPL-3.0 here while carrying AGPL's reputation as the single most contributor-chilling common OSI license (many companies have blanket internal bans on AGPL specifically, more so than plain GPL). Adopting AGPL would also be the license that made depending on MuPDF "free" — worth being explicit that these are two separable decisions R8 poses together but that do not have to be bundled; OpenConvert's Apache-2.0 choice is independent of, and reinforces, the MuPDF exclusion in §5.

## 5. Redistribution mechanics

**LICENSE + NOTICE files, written beside every downloaded artifact.** The model manager (Rust, `oc-net`, D9) writes `LICENSE` and `NOTICE` files into the model's own directory at download time, alongside the GGUF — this applies uniformly to models, the OCR pack, and the validation pack (§6), not only to the default model. For Apache-2.0 models this is a standard NOTICE; for any conditionally-permissive model offered in the future (Gemma-family, Llama-family, LFM-family) the download flow must actually **surface** the license terms to the user before or during download, not merely write a file after the fact — a license requiring a "provide a copy of the agreement" step is not satisfied by a file nobody sees.

**NOTICE for ported PdfPig algorithms.** `oc-layout`'s reading-order and layout-segmentation code (Docstrum-style clustering, XY-cut with pre-masking, nearest-neighbour word extraction, unsupervised reading-order detection) is a **port** of PdfPig's (Apache-2.0) equivalent algorithms — pure geometry over `(char, x, y, w, h, fontsize)` tuples, no PDF-format-specific code, no PdfPig dependency at runtime (R6 §3.6). Apache-2.0 requires a NOTICE file be preserved/included for any derivative distribution; OpenConvert's own `NOTICE` file at the repository root credits PdfPig and UglyToad/PdfPig's contributors for the ported algorithms specifically, distinct from the general third-party NOTICE aggregation described below.

**SBOM per release.** A CycloneDX-format Software Bill of Materials is generated for each release build (`cargo-cyclonedx` or equivalent for the Rust workspace, an npm-side SBOM tool for any JS build tooling) and published alongside release binaries — this is both increasingly expected practice for security-conscious OSS distribution and a prerequisite for downstream packagers/distros to do their own vulnerability tracking against OpenConvert's exact pinned dependency versions (R8 §A8).

**`cargo-deny` allow-list and deny-list, exact configuration.** Enforced in CI on every build, not merely documented:

- **Licenses allow-list:** MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, MPL-2.0 (Saxon-HE, invoked externally, never linked — allowed at the allow-list level for completeness even though it never actually appears in the linked Rust dependency graph), Unicode-3.0 (or whichever current Unicode data license applies), CC0-1.0 (test-corpus/data only, never a code dependency).
- **Licenses deny-list:** AGPL-3.0, GPL-2.0, GPL-3.0, LGPL-2.1, LGPL-3.0 (LGPL specifically denied for *linked* crates — see §9's note on the validation pack's JRE, which is a distinct, non-linked case), and any "Non-standard"/unrecognized SPDX result, which `cargo-deny` treats as a build failure requiring an explicit, reviewed exception rather than a silent pass.
- **Bans:** duplicate-version detection (dependency-tree bloat control) and an explicit deny entry for any HTTP-client crate (`reqwest`, `ureq`, `hyper` as a client) in every workspace member **except** `oc-net` (D13.9) — this is the mechanism, not merely the design note, that makes the "core has no network access" claim in `SECURITY.md` auditable by `cargo tree`, not just assumed.
- **Sources:** crates.io only by default; any git-source dependency requires an explicit, reviewed allow-list entry, closing the dependency-confusion/typosquat-via-unexpected-git-source class of supply-chain risk.

## 6. The "packs" concept

D6 and D9 both establish the same distribution pattern for anything too large or too specialized to bundle in the ~35–45 MB base install (D12): an optional, post-install, SHA-256-pinned, license-labeled download, never fetched during a conversion (D13.9). Four packs exist or are anticipated for v1 and its immediate follow-on:

| Pack | Contents | License shown in UI | Size (approx) |
|---|---|---|---|
| **Model pack** | A GGUF for the chosen LLM tier | Per-model, from the table in §4 — surfaced before download for any conditionally-permissive model | 400 MB – 1.7 GB depending on tier |
| **OCR pack** | Tesseract binary + `tessdata_fast` language files (D4) | Apache-2.0 (Tesseract, tessdata) + BSD-2-Clause (Leptonica) | ~10–20 MB core, plus per-language `tessdata` files |
| **Validation pack** | A jlink'd minimal JRE + `epubcheck.jar` (D6) | See below — **the JRE's own license must be verified per vendor** | ~40–50 MB |
| **Dictionary packs** | Per-language hunspell-style dictionaries beyond the CC0-derived core word-frequency lists (§9) | Per-source — en_US is permissive/SCOWL (clean); de_DE/tr_TR packs are explicitly optional precisely because their upstream licenses (igerman98 GPL-family; tr hunspell MIT-badge-unverified) are not yet confirmed clean enough to bundle as core data | Small (single-digit MB per language) |

**The validation pack's JRE licensing needs explicit, vendor-specific verification before it ships.** A jlink'd minimal runtime built from OpenJDK-derived sources (e.g., Eclipse Temurin) is generally redistributable under the **GPL v2 with the Classpath Exception** — the Classpath Exception is specifically what makes linking/bundling a JRE not trigger GPL's copyleft on the application using it, which is why this is workable at all for an Apache-2.0 project. But this is a per-JDK-vendor question, not a universal one: the exact license terms, any additional vendor-specific redistribution conditions, and whether the specific jlink'd module set used stays within the Classpath-Exception-covered scope all need direct verification against whichever JDK distribution is actually chosen (Temurin is the leading candidate, not yet confirmed) before the validation pack ships. This is flagged here as a concrete pre-ship verification task, not asserted as already resolved — R8's own research did not reach this level of JRE-vendor-specific licensing detail, and D6's text itself calls the pack "same download mechanism as the model" without addressing the JRE-license question directly.

Each pack's license is shown in the model manager / pack-management UI (`UI_UX.md` §"Settings") before or during download, with the accepted license recorded in the app's local state — this is both the compliance mechanism for conditionally-permissive packs and the honesty mechanism for a project whose pitch depends on users trusting what it downloads and why.

## 7. Contributor policy

**DCO sign-off, no CLA** (D15's own framing carried forward explicitly, since it is load-bearing for the Apache-2.0-vs-GPL trade-off discussed in §1). Every commit is signed off (`git commit -s`) under the Developer Certificate of Origin, asserting the contributor has the right to submit the contribution under the project's license. No Contributor License Agreement is required. This is a deliberate choice, not an oversight: a CLA would be the mechanism that keeps a future re-licensing or dual-licensing option cleanly available (every contributor's rights are pre-consolidated), and D15/R8 both note that Apache-2.0's own patent grant plus the DCO's simpler contributor experience is judged worth forgoing that option's cleanliness — consistent with the project's stated priority of maximizing the contributor pool over preserving maximum future licensing flexibility.

## 8. Trademark note for Project Gutenberg files

Project Gutenberg's own distributed files carry the "Project Gutenberg License": redistribution is unrestricted only if the file is either (a) kept **verbatim**, with the full PG license/header attached, or (b) the PG header/references are stripped entirely, at which point the underlying text's own (typically US-public-domain) copyright status governs with no PG-specific restriction (R7 §A.0 item 1). **Using the "Project Gutenberg" name or trademark in a title or in promotional material is separately governed by PGLAF's trademark terms**, and charging money for a distribution that retains PG attribution triggers a 20%-of-gross-profits royalty obligation to PGLAF. OpenConvert's practical posture, consistent with R7's own recommendation: pull the plain-text or HTML edition, strip the PG boilerplate before using the text as ground-truth-generation input or corpus material, and never redistribute PG's own packaged files with the header intact while also claiming format freedom. This is a corpus/test-material concern, not a shipped-product dependency concern — but it belongs in this document because Standard Ebooks and Project Gutenberg are adjacent, easily conflated sources with materially different license postures (CC0 outright vs. conditional-verbatim-or-strip), and R7's corpus research treats Standard Ebooks (CC0, §2.2) as the primary ground-truth source specifically to avoid this trademark and royalty surface entirely.

## 9. Checklist for adding a dependency

Before a new crate, native tool, model, or data file is added anywhere in the shipped dependency tree (Rust workspace, native sidecars, packs):

1. **Identify the exact license via a primary source** — the crate's own `Cargo.toml`/`LICENSE` file or the model card's raw YAML frontmatter, not a mirror site, a badge, or a secondary summary. V2's own research found a mirror (`lib.rs`) returning stale, contradicted-by-primary-source data for `pdfium-render` — badges and mirrors are a starting point for discovery, never the confirming source.
2. **Check it against the `cargo-deny` allow-list (§5)** before writing a single line of code that depends on it. A dependency that would fail CI is caught at proposal time, not at merge time.
3. **If the license field is anything other than a recognized SPDX identifier** (crates.io's own `"Non-standard"` flag on `zspell` is the concrete example already found — §2.1), **stop and manually read the actual license text** before proceeding, regardless of how permissive the crate's description or README makes it sound.
4. **For a model:** confirm commercial-use, redistribution, and modification terms independently — a model card's high-level "Apache-2.0" badge is usually right (Qwen3/3.5, Gemma 4 all confirmed this way) but has been wrong before at the family level (Gemma ≤3 vs. Gemma 4; the R8→V1 correction in §4 is the concrete example) and needs its own raw-license-file fetch, not an inherited assumption from a prior model generation in the same family.
5. **For anything bundled as data rather than code** (dictionaries, word-frequency lists, hyphenation patterns, corpus fixtures) — apply the same rigor as to code. D15's own resolution of the German-dictionary problem is the model to follow: rather than bundling igerman98 (GPL family, unverified exact terms — §2, §3), OpenConvert generates its own EN/DE/TR word-frequency lists as **core data from CC0/PD source text** (Standard Ebooks, DTA's explicitly-unrestricted plain-text export, Wikisource-TR) using its own tooling, so no GPL dictionary is bundled at all; hunspell-format packs remain an optional, separately-licensed later addition (§6) rather than a default-install dependency. The small hyphenation-classifier weights (a kilobyte-scale CRF/logistic model, trained by `eval/` tooling — R2/RED_TEAM §A1) are committed to the repository as project-original, project-licensed artifacts, sidestepping the third-party-hyphenation-pattern-license question in §2.1 for the default install path.
6. **Record the finding in this document and in `cargo-deny`'s configuration together, in the same change** — a license decision that lives only in a PR description is not durable; it belongs in the allow-list (or the excluded-set table, §3) and in this document's dependency table (§2) as one atomic update.
7. **If the dependency is GPL/AGPL and the intended use is "invoke as an external process, never link"** — treat this as requiring explicit sign-off from the Chief Architect, not a default green light. R8's own finding stands: whether arm's-length subprocess invocation of a copyleft tool avoids triggering copyleft obligations for a *shipped* product is a fact-specific, unsettled question under FSF's own guidance on "mere aggregation" versus a "combined work," and this project does not rely on that boundary for anything it ships (the one exception, `pdftotext`/Poppler as a CI-only, never-shipped-to-users differential oracle, is deliberately scoped to avoid the shipped-product version of this question entirely — §3).
